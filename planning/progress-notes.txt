MCP SERVER: Fixed `..` trigger failing at session start due to MCP cold-start race.

  ROOT CAUSE: Claude Code spawns the MCP server process on session open, but the
  `..` shorthand fires on the very first user message — before Python has finished
  the stdio MCP handshake (~1-2s). Tools appear as "deferred / still connecting"
  and the direct call to mcp__orionforge__load_default fails.

  FIX 1 — Memory trigger updated (feedback_kos_trigger.md):
    `..` now first calls ToolSearch(`select:mcp__orionforge__load_default`) as a
    ready-gate (ToolSearch blocks until connecting servers are available), then
    calls load_default. This makes the trigger reliable regardless of spawn time.

  FIX 2 — Lazy engine init (orion-ui-standalone/mcp_server/orion_mcp.py):
    Moved `engine = OrionEngine()` from module-level to a lazy `_get_engine()`
    singleton. The MCP process now completes its handshake (tool registration)
    before doing any filesystem/FAISS work — shaving response latency off the
    critical path and making cold-start faster.

  COLD-START DEEP DIVE (Opus pass) — profiled the first `..` end-to-end:
    Original cold summon ~47s. Profiling the cache-hit path showed the time split:
      import faiss ............................ 0.6s
      import sentence_transformers (+torch) .. 24.7s   <-- 93% of cold time
      NotesFAISS.load + model dim-check ....... 0.9s
      encode 1 query .......................... 0.04s
    Two problems found and fixed:

    FIX 3 — Soul-index fingerprint cache (mcp_server/engine.py _get_notes_faiss):
      The engine ALWAYS called build_index() — re-embedding ~1024 soul-script
      chunks (~20s) on every fresh process — even though NotesFAISS.load() exists.
      Now we hash the soul-script corpus (sha256 of chunk text) into
      data/memory/mcp_soul_faiss/soul_fingerprint.txt; if the hash matches we load
      the cached index instead of rebuilding. Auto-rebuilds when any soul script
      changes. (The vault FAISS already did load-or-build; only the soul index was
      rebuilding.) Cut cold summon 47s -> 27s.

    FIX 4 — Background warm-up (engine.warm() + _warm_in_background in orion_mcp.py):
      The torch/sentence-transformers import (~25s) is lazy, so it landed on the
      first `..`. The MCP server process spawns at session open and sits idle until
      the user types — so we now warm the engine (heavy import + model + FAISS) in
      a daemon thread at startup, overlapping it with that idle time. Tool
      registration / handshake still runs synchronously in the main thread, so the
      tools-available time is unaffected. A threading.Lock in OrionEngine does
      double-checked locking on both lazy index builders so a `..` arriving mid-warm
      shares the one build (no double-embed, no crash). Gate off with
      ORION_MCP_WARM=0.

    RESULT (verified): user-felt first `..` after warm = ~50ms (was 47s). Race test
      (summon concurrent with warm) returns a valid persona, 0 errors, build count 0.
      Three complementary layers now: ToolSearch ready-gate (tool is callable) ->
      lazy init (handshake stays fast) -> background warm (engine hot when called).

  FUTURE: If startup is still slow, consider switching .mcp.json to use `uv run`
    instead of bare `python` — uv caches the venv and cuts Python startup by ~40%.
    The torch import (~25s) is the real floor; excluding the Python/site-packages
    dir from Windows Defender real-time scan would cut it materially.
